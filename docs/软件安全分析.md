# 软件安全分析

## 分析背景

本软件为本地桌面应用程序，运行于用户个人电脑，不涉及网络传输和远程访问。
本文档为 v2 版本（Tauri 2.x + rusqlite）的安全分析，相较 v1（Electron + sql.js）在多个安全维度有改进。

## 安全设计评估

### 1. 文件系统安全 ✅ 优秀

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 读取文件系统 | ✅ 安全 | Rust 端 `fs::read_dir`、`fs::metadata`，仅用于扫描与 stat |
| 打开文件 | ✅ 安全 | 通过 `tauri-plugin-shell` 调用系统默认程序打开，路径由用户操作产生 |
| 用资源管理器打开 | ⚠️ 注意 | `open_in_explorer` 使用 `Command::new("explorer")` 启动子进程，参数来自用户选定文件 |
| 删除文件 | ✅ 安全 | **未实现任何文件删除功能**，不提供删除实体文件的能力 |
| 写入文件系统 | ✅ 安全 | 仅在 sqlite 持久化、`<uuid>.tag` 文件创建时写入 |
| 路径校验 | ⚠️ 无校验 | 路径由用户在前端传入，未做白名单校验 |

**结论：** 应用不会意外修改或删除用户的任何业务文件。`open_in_explorer` 虽启动新进程，但参数完全可控（仅由用户点击触发），风险等同于手动在资源管理器中打开。

**`<uuid>.tag` 文件写入说明：**
- 仅在用户首次给文件夹打标签时创建
- 文件名是 UUID，内容是 UUID 字符串，无可执行内容
- 写入位置是用户当前浏览的文件夹，不超出用户授权范围

---

### 2. 进程隔离安全 ✅ 优秀

Tauri 2.x 的进程模型与 Electron 完全不同，安全性有本质提升。

| 配置项 | 当前值 | 风险 |
|--------|--------|------|
| 进程模型 | 单进程（Rust 主进程 + WebView2 渲染进程） | ✅ 无 Electron 的多进程复杂度 |
| capabilities 权限 | 最小化 | ✅ 仅声明 `core:default`、`core:event:allow-listen`、`core:webview:allow-internal-toggle-devtools`、`dialog:default`、`shell:allow-open` |
| Tauri 命令注册 | 显式 `invoke_handler!` 枚举 | ✅ 未注册的命令无法被前端 invoke |
| WebView 沙箱 | 由 WebView2 / WKWebView / WebKitGTK 强制启用 | ✅ 渲染进程不能直接访问操作系统 |

**v1 → v2 改进：**
- 不再有 `contextIsolation` / `nodeIntegration` 等 Electron 概念，因为渲染进程是真正的浏览器引擎（WebView2 / WKWebView / WebKitGTK），与 Node.js 完全隔离
- 所有「特权操作」必须通过 Rust 命令暴露，权限由 capabilities 集中管理

**结论：** 恶意前端代码（即便是 XSS）也只能调用已注册的命令，无法直接执行任意系统调用或访问任意文件路径。

---

### 3. 数据库安全 ✅ 安全

| 检查项 | 状态 | 说明 |
|--------|------|------|
| SQL 注入 | ✅ 安全 | rusqlite 强制使用 `params!` 绑定参数，所有变量均走参数化通道 |
| 数据删除 | ✅ 安全 | `delete_file` 仅删除数据库元数据记录，不涉及实体文件 |
| 数据存储 | ✅ 安全 | 数据库文件 `tags.db` 存放在 exe 同级目录，与用户业务文件隔离 |
| 数据库连接 | ✅ 安全 | `parking_lot::Mutex<Connection>` 单例保护，并发安全 |

**数据库删除操作说明：**
- `delete_file` — 从 files 表删除记录，**不删除磁盘上的实际文件**
- `delete_tag` — 从 tags 表删除标签，仅清理元数据（同时通过 CASCADE 清理 file_tags 关联）
- `delete_tag_group` — 从 tag_groups 表删除分组，自动解绑分组内标签的 group_id

**v1 → v2 改进：**
- 不再有 sql.js wasm 加载环节，去掉 wasm 相关的供应链风险
- 数据库连接在 Rust 端常驻，前端无法直接接触 SQL 字符串
- 所有 SQL 操作都在 `with_conn` 闭包内串行执行，杜绝并发冲突

---

### 4. 命令执行安全 ✅ 良好

| 检查项 | 状态 | 说明 |
|--------|------|------|
| get_drives | ✅ 安全 | 不再调用 PowerShell，改用 Win32 API `GetLogicalDrives` + `GetDriveTypeW` + `GetDiskFreeSpaceExW` |
| sync_folder | ✅ 安全 | 仅计算文件 hash 与 SQL 写库，不执行任何文件操作 |
| open_file | ✅ 安全 | 通过 `tauri-plugin-shell` 打开文件，路径由用户操作决定 |
| open_in_explorer | ⚠️ 注意 | `Command::new("explorer")` 启动子进程，参数为单一路径字符串，无 shell 拼接 |
| read_folder_tag | ✅ 安全 | `fs::read_dir` + 后缀过滤 + `fs::read_to_string` 读取单文件 |
| create_folder_tag_file | ✅ 安全 | UUID 由 `uuid::Uuid::new_v4()` 生成，文件名/内容安全 |

**v1 → v2 改进：**
- `getDrives` 不再调用 PowerShell 子进程，启动更快、无 shell 注入面
- `open_in_explorer` 用 `Command::new` + `arg`，不走 shell 解释，无命令注入风险

**`open_in_explorer` 风险分析：**
- Rust 中 `Command::new("explorer").arg(&path)` 在 Windows 上不会经过 cmd.exe 解释
- 攻击者必须能伪造一个"看起来是文件路径但实际是参数"的输入；前端 UI 只允许用户从 Rust 返回的 `ScanFile.path` 字段取值，路径已经过 OS 文件系统层解析，可信度高
- 即便被注入 `explorer.exe "D:\foo && calc.exe"`，也会被 `arg` 当作单个参数加引号，命令不会拼接

---

### 5. IPC（前端 ↔ Rust）通信安全 ✅ 优秀

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 参数类型 | ✅ 强类型 | Tauri 2.x 自动反序列化 JSON，Rust 端签名强类型校验 |
| 参数范围 | ⚠️ 无校验 | 数值范围未做白名单，但 Rust 函数逻辑会做幂等性 / 存在性判断 |
| 路径校验 | ⚠️ 无校验 | 路径未做白名单校验，但所有操作仅作用于已扫描的路径 |
| 鉴权 | ⚠️ 无 | 本地运行，无用户体系 |
| capabilities | ✅ 集中管控 | 只注册必要的命令与权限 |

**说明：** 与 v1 不同，v2 渲染进程与 Rust 主进程之间是**类型化 IPC**，每个 `#[tauri::command]` 函数都通过 Rust 类型系统校验入参。恶意前端不能直接构造任意 IPC，必须走 invoke 通道。

**纵深防御建议：**
- 未来若引入用户数据加密，可在 Rust 端对 `path` 参数增加「必须在白名单目录」的运行时校验
- 数值范围校验优先级低，因为所有写操作都有 UNIQUE / FOREIGN KEY 约束保护

### 6. 哈希计算安全 ✅ 安全

| 检查项 | 状态 | 说明 |
|--------|------|------|
| hash 算法 | ✅ 安全 | sha256 由 `sha2` crate 实现，工业标准 |
| hash 范围 | ✅ 安全 | 仅计算文件头尾各 1MB，避免全文件读取 |
| hash 用途 | ✅ 安全 | 仅用于文件身份识别，不涉及加密、签名、密码学 |
| 缓冲区安全 | ✅ 安全 | 严格按 `BUFFER_SIZE` 边界读写，无溢出风险 |

## 本地运行场景的特殊性

### 攻击者模型

本地运行的软件面临的威胁模型与网络应用不同：

| 威胁来源 | 可能性 | 防护优先级 |
|----------|--------|------------|
| 远程攻击者 | ❌ 极低 | 不需要（无网络功能） |
| XSS | ⚠️ 理论 | 渲染进程是隔离的浏览器引擎，但若前端代码被 XSS 仍可调用已注册命令 |
| 本地恶意软件 | ⚠️ 已中招 | 需防恶意软件而非本软件 |
| 用户误操作 | ⚠️ 可能 | 需在 UI 上明确提示 |
| 开发者失误 | ⚠️ 可能 | 已通过禁用文件操作保障 |

### 防护策略调整

本地场景下，**真正的威胁来自其他恶意软件**，而非本应用本身。本软件的安全策略重点：

1. 不提供删除文件的能力 → ✅ 已实现
2. 不提供执行任意命令的能力 → ✅ 已实现（所有命令都是固定语义的）
3. 不暴露敏感数据到外部 → ✅ 已实现（无网络功能）
4. 不引入高风险依赖 → ✅ 已实现（移除 PowerShell、sql.js、Electron）

## v1 → v2 安全维度对比

| 维度 | v1（Electron） | v2（Tauri） | 改进 |
|------|----------------|------------|------|
| 进程模型 | 主 + 渲染 + GPU 多进程 | 单 Rust 进程 + WebView2 | 攻击面更小 |
| 渲染进程隔离 | contextIsolation | WebView2 内置沙箱 | 更彻底 |
| Node.js 暴露 | nodeIntegration:false | 完全无 Node.js | 风险归零 |
| SQL 注入 | 参数化 | rusqlite 强制参数化 | 等同 |
| 数据库加载 | sql.js wasm | rusqlite 原生 | 去 wasm 供应链 |
| 磁盘枚举 | PowerShell 子进程 | Win32 API | 减少进程数 |
| 资源管理器打开 | shell.openPath | Command::new explorer | 等价（更显式） |
| IPC 类型化 | JSON 无校验 | Rust 强类型 | 改进 |
| 依赖数量 | 较多（Electron 全家桶） | 较少（仅 Tauri 核心） | 供应链更小 |

---

## 总结

| 维度 | 评分 | 说明 |
|------|------|------|
| 文件系统安全 | ⭐⭐⭐⭐⭐ | 不删除文件，不修改文件 |
| 进程隔离 | ⭐⭐⭐⭐⭐ | Tauri 单进程 + WebView2 沙箱 |
| 数据库安全 | ⭐⭐⭐⭐⭐ | rusqlite 强制参数化 + Mutex 保护 |
| 命令执行 | ⭐⭐⭐⭐ | 子进程参数严格、shell 注入面极小 |
| IPC 安全 | ⭐⭐⭐⭐⭐ | Rust 强类型 + capabilities 集中管控 |
| 哈希计算 | ⭐⭐⭐⭐⭐ | sha256 标准实现 |
| 日志隐私 | ⭐⭐⭐⭐⭐ | 无文件日志，无网络外泄 |
| 依赖供应链 | ⭐⭐⭐⭐⭐ | 移除 sql.js / PowerShell / Electron |

**总体评价：** v2 在本地运行场景下安全性优于 v1，进程模型更简单、依赖更少、攻击面更小。主要风险点已被有效防护。无需过度加强安全措施，建议将精力投入到功能完善上。
